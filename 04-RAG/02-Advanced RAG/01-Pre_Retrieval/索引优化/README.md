
# RAG 的索引优化

这四种都属于 RAG 检索前索引优化，核心目标是：**让"存入向量库的知识块"更容易被命中，并且在命中后能给 LLM 更合适的上下文**。 它们不是互相替代关系，通常会根据文档结构和查询场景组合使用。

## 1. 摘要索引

### 要解决的问题

很多文档不是纯文本，还包含表格、参数表、图片说明、流程图描述等半结构化内容。如果直接按固定长度切块，表格会被切碎；如果整表向量化，又容易丢失结构语义，导致检索不准。

### 核心思路

对每个文档块生成一个"摘要向量"，检索时先匹配摘要，再回溯到原始块。

### 离线构建流程

1. 文档分块，块可以相对大一些，尤其要保留表格、段落结构。
2. 用 LLM 为每个块生成摘要。
3. 将摘要向量化，存入向量库。
4. 摘要与原始块通过 ID 关联；原始块可单独存储。
5. 检索时匹配摘要向量，再取回原文块作为上下文。

### 适用场景

- 企业年报、财务报表、利润表等表格密集文档
- 医疗药品说明书、临床数据表
- 工业技术文档、设备参数表
- 含流程图、规格说明的半结构化文档

### 优缺点

- **优点**：摘要更凝练，语义更聚焦，能绕过表格直接嵌入效果差的问题。
- **缺点**：摘要可能丢失细节；离线生成摘要会消耗较多 Token。

## 2. 父子索引

### 要解决的问题

检索希望块小，语义集中；但生成答案希望块大，上下文完整。单一粒度切块往往顾此失彼。

### 核心思路

把文档分成"父块"和"子块"。子块用于检索，父块用于返回给 LLM。

### 离线构建流程

1. 对文档做层级切块：父块较大，子块较小。
2. 子块单独做 embedding 并建立向量索引。
3. 每个子块记录父块 ID，父块内容单独存储。
4. 检索时匹配子块，再根据父 ID 取回完整父块。

### 适用场景

- API 文档、技术手册
- 书籍、论文、法律条款
- 代码库文档
- 有清晰章节层级的长文档

### 优缺点

- **优点**：检索更精准，同时保留完整上下文，减少碎片化。
- **缺点**：索引结构更复杂；父块过大时可能引入噪声，需要控制父块长度。

## 3. 假设性问题索引

### 要解决的问题

用户提问往往口语化、表达多样，而文档块通常是书面化陈述。直接用"问题向量"匹配"文本块向量"，有时语义距离较远。

### 核心思路

离线阶段让 LLM 为每个文档块预生成若干假设性问题，并把这些"问题向量"存入索引。检索时变成"问题对问题"的匹配。

### 离线构建流程

1. 文档分块。
2. 对每个块让 LLM 生成若干可能提问，例如 3-5 个。
3. 将这些假设性问题向量化并入库。
4. 每个问题向量与原始块绑定。
5. 检索时匹配问题向量，再取回对应原文块。

### 适用场景

- 客服问答
- 技术文档查询
- 培训资料
- 用户问法多变、表达模糊的场景

### 优缺点

- **优点**：能覆盖多种问法，提升召回率；尤其适合"同一知识点多种提问方式"的场景。
- **缺点**：问题质量依赖 LLM；可能引入噪声；索引体积会增加。

## 4. 元数据索引

### 要解决的问题

当文档来源多、规模大、时效性强时，单纯靠向量相似度检索容易把不同来源、不同时间、不同业务域的内容混在一起。

### 核心思路

给每个文档块补充结构化元数据，例如来源、作者、时间、文档类型、业务域、版本号等。检索时先用元数据过滤，再做向量检索。

### 离线构建流程

1. 解析文档时提取元数据字段。
2. 将元数据写入索引的过滤字段。
3. 向量字段用于语义检索，元数据字段用于预过滤或后过滤。
4. 查询时根据用户意图选择过滤条件，例如只查"2025年之后""某产品线""某部门文档"。

### 适用场景

- 多来源知识库
- 企业内部文档系统
- 有时效要求的政策、制度、产品文档
- 需要按部门、版本、状态筛选的场景

### 优缺点

- **优点**：显著缩小检索范围，降低干扰；便于做权限控制、时效控制。
- **缺点**：依赖元数据质量；如果元数据缺失或标注不一致，效果会下降。

## 四种索引对比

| 索引类型 | 核心机制 | 主要收益 | 典型代价 | 最适合场景 |
|---|---|---|---|---|
| 摘要索引 | 用摘要向量检索，再回溯原文 | 提升半结构化内容召回 | 离线生成摘要成本高 | 表格、年报、说明书 |
| 父子索引 | 子块检索，父块返回 | 兼顾精准召回与完整上下文 | 索引结构更复杂 | API文档、书籍、法律文本 |
| 假设性问题索引 | 预生成问题向量，问题对问题匹配 | 覆盖多种问法，提升召回 | 问题质量不稳定 | 客服、FAQ、多问法场景 |
| 元数据索引 | 用标签/字段过滤后再检索 | 缩小检索范围，减少干扰 | 依赖元数据完整性 | 多来源、多版本、时效文档 |

## 组合使用建议

实际搭建 RAG 后端时，可以把它们放在离线索引构建阶段统一设计：

- **文档结构复杂、含表格**：优先加摘要索引。
- **长文档、层级清晰**：优先用父子索引。
- **用户问法多样、表达模糊**：加假设性问题索引。
- **文档来源多、需要过滤**：必须补元数据索引。
- **生产系统**：通常不是四者全上，而是先保证元数据索引和父子/摘要索引，再根据召回率瓶颈引入假设性问题索引。
