## 文档分块

### 一、为什么要文档分块
- **技术层面**：无论是嵌入模型还是大模型，它们的上下文长度都是有限的，不能将加载的整个文档扔进去，需要将文档切分成**合适大小**的**块（chunk）**
- **业务层面**：用户问的问题只是与整个知识库中某个块中的内容有关，只需要附带与问题相关的文档块就行。如果将整个文档扔给大模型，会导致 token 消耗量增加、处理速度变慢、引入过多的噪声（无关内容）

> #### **块大小核心矛盾** <br>
> - **块大： 向量语义越泛化，语义完整度高**
>   - 优点：上下文完整
>   - 缺点：噪声多，检索精度低；过大可能超出嵌入模型和大模型的上下文限制
> - **块小：向量语义越精准，语义完整度低**
>   - 优点：语义精准，检索精度高
>   - 缺点：缺少上下文；过小可能导致一句话在中间截断，语义不完整；检索时匹配很多碎片化信息，难以拼出完整答案

### 二、文档分块方法
LangChain中提供了各种不同的切分策略，并且提供了统一的接口：`TextSplitter`
- split_text(text: str) -> list[str]
- split_documents(documents: Iterable[Document]) -> list[Document]

| 方法 | 核心原理                                               | 优缺点                                                                       | 适用场景                   |LangChain 类 |
|---|----------------------------------------------------|---------------------------------------------------------------------------|------------------------|---|
| 固定长度切分 | 按预设字符数 chunk_size 直接切分，可设置重叠窗口 chunk_overlap       | 优点：实现简单、计算效率高、块大小均匀；<br>缺点：容易在句子或段落中间截断，语义完整性差                            | 结构性弱的纯文本，或数据预处理初期的基线方案 | `CharacterTextSplitter`  |
| 分隔符切分 | 按单一分隔符切分，如换行符`\n`、空格` `、句号`。`、逗号`,`等               | 优点：可在语义自然边界处切分，比固定长度更可控；<br>缺点：长段落仍可能仍然超出模型限制，某些句子也可能过短                   | 段落边界清晰、结构简单、语义复杂度较低的文本                    |`CharacterTextSplitter` |
| 递归切分 | 按分隔符优先级逐层切分：段落`\n\n` → 行`\n` → 句子`。` → 字符，直到每块符合长度 | 优点：通用性强，在"保持语义边界"和"控制块大小"之间取得平衡；<br>缺点：分隔符配置不当会导致块粒度失衡，极度格式化文本（表格/代码）效果一般 | 通用 RAG 默认方案    | `RecursiveCharacterTextSplitter` |
| 结构切分 | 依据 Markdown 标题、HTML 标签、代码函数等原生结构切分                 | 优点：保留文档层级，检索时可以定位到具体章节；<br>缺点：依赖文档结构规范，对无结构文本效果有限                              | Markdown 技术文档、README、HTML 页面、API 文档、代码文档                  | `MarkdownHeaderTextSplitter` / `HTMLHeaderTextSplitter` |
| 语义切分 | 用嵌入模型计算相邻句子相似度，在低于阈值的语义跳变处切分                       | 优点：块内主题更连贯，语义完整性高；<br>缺点：计算成本高，需要嵌入模型和阈值调优                                | 法律、医疗、政策等高质量知识库，以及对检索精度要求较高的场景                    | `SemanticChunker` |
